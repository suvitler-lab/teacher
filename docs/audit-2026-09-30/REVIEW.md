## บั๊กที่ควรแก้ก่อนเปิดใช้งานจริง

### N01 — P1: ย้อนกลับการล้างทำให้คะแนนเกินคะแนนเต็ม

**ทำซ้ำได้โดยไม่ต้องมีการเขียนพร้อมกัน:**

1. ให้คะแนนนักเรียน 9/10
2. ล้างคะแนนทั้งห้อง
3. แก้งานให้คะแนนเต็มเป็น 5 — API อนุญาต เพราะคะแนนปัจจุบันถูกล้างแล้ว
4. เรียกย้อนกลับการล้าง batch เดิม

**ผลจริง:** ทุกขั้นตอบ HTTP 200 และฐานข้อมูลมี `score=9, full_score=5` การป้องกันบั๊ก B05 เดิมแก้ในทางให้คะแนน/แก้งานแล้ว แต่ทาง bulk-undo ยังสร้าง 9/5 ได้

**สาเหตุ:** undo ตรวจ epoch และว่าช่องคะแนนมีการแก้หลัง bulk หรือไม่ แต่ไม่ตรวจคะแนนที่จะคืนกับคะแนนเต็มปัจจุบัน ก่อนเรียก upsert ที่ไม่มี guard ของงาน

จุดแก้: [bulk-undo ในสำเนา ZIP](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/worker/routes/submissions.ts:529)

**แนวแก้:** ตรวจคะแนนของทุกแถวที่จะคืนกับงานปัจจุบันภายในธุรกรรมเดียวกับ undo ถ้าคะแนนเต็มเปลี่ยนจนคืนไม่ได้ ให้ปฏิเสธทั้ง batch พร้อมข้อความชัดเจน ห้ามลดคะแนนของเด็กให้เอง ควรตรวจสถานะลบงานและความสัมพันธ์ที่ undo ต้องรักษาใน guard เดียวกัน

**เกณฑ์ผ่าน:** ขั้นตอน 9/10 → ล้าง → เต็ม 5 → undo ต้องปฏิเสธอย่างชัดเจน ไม่เกิด 9/5 และไม่มี audit ว่าคืนสำเร็จ

### N02 — P1: ข้อมูลก่อนล้างใน audit ล้าสมัย ทำให้ undo คืนคะแนนผิด

**ทำซ้ำได้โดยควบคุมคำขอจากสองเครื่อง:**

1. คะแนนเริ่มต้น 5
2. คำขอล้างอ่านคะแนน 5 แล้วหยุดก่อน DB batch
3. รายการจากอีกเครื่องที่เกิดก่อนคำสั่งล้าง แต่เพิ่งส่งถึงระบบ บันทึกคะแนน 7 สำเร็จ
4. ปล่อยคำขอล้างให้บันทึก จากนั้นกด undo

**ผลจริง:** ก่อนการล้างลงฐานมีคะแนน 7 แต่ undo คืน 5 โดยตอบสำเร็จ นี่คือผลต่อข้อมูลจริงจากข้อจำกัด `audit.before` ที่ STATUS เดิมระบุไว้ ไม่ใช่เพียงประวัติที่แสดงไม่ตรง

**สาเหตุ:** `before_json` มาจากการอ่านก่อนธุรกรรม ในขณะที่ guard อนุญาตให้คำสั่งล้างที่เกิดภายหลังทับคะแนน 7 ได้ตามลำดับเหตุการณ์ แล้ว undo เชื่อ `before_json` นั้น

จุดแก้: [สร้าง audit ของ bulk](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/worker/routes/submissions.ts:434), [undo อ่าน before_json](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/worker/routes/submissions.ts:504)

**แนวแก้:** บันทึก before จากแถวจริงที่กำลังจะถูกแทนภายในธุรกรรมเดียวกัน หรือใช้ version guard ปฏิเสธ bulk เมื่อข้อมูลเปลี่ยนหลังการอ่าน แล้วให้ผู้ใช้โหลดใหม่และลองอีกครั้ง การตรวจเพียงว่า operation ชนะและเขียนจริงไม่พอ ต้องตรวจความถูกต้องของ before ด้วย

**เกณฑ์ผ่าน:** ในกรณีนี้ต้องคืน 7 หรือปฏิเสธการล้างตั้งแต่พบ conflict ห้ามตอบสำเร็จแล้วคืน 5

### N03 — P2: หน้า Scan อาจพลาดรายการจากเครื่องอื่นไปตลอดรอบนั้น

**ทำซ้ำได้ 2 รูปแบบ:**

- GET submissions อ่านรายการว่าง → อีกเครื่องบันทึก 9 สำเร็จ → GET แรกค่อยตอบด้วย `serverTime` หลังการบันทึก → poll ถัดไปใช้ `since=serverTime` และไม่พบรายการนั้น
- POST คะแนนเริ่มก่อน poll และกำหนด `updated_at` ไว้แล้ว แต่ยังไม่ commit → poll ตอบรายการว่างและเวลาใหม่ → POST ค่อย commit → poll ถัดไปก็ไม่พบรายการนั้น

**ผลจริง:** ฐานข้อมูลมีคะแนน 9 แต่ผล poll แรกและครั้งถัดไปว่างทั้งหมด ไม่ใช่คะแนนหายจากฐาน แต่ผัง/จำนวนส่งงานของอีกเครื่องไม่ตรงและอาจค้างจนโหลดข้อมูลเต็มใหม่

**สาเหตุ:** cursor ใช้เวลาตอบ GET ส่วน `updated_at` ใช้เวลาเริ่มคำขอเขียน จึงไม่ใช่ตัวบอกลำดับ commit และมีช่วงที่รายการหลุดจากเงื่อนไข `updated_at > since` ได้

จุดแก้: [GET submissions](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/worker/routes/submissions.ts:36), [Scan polling](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/src/pages/Scan.tsx:157)

**แนวแก้สำหรับรอบนี้:** อ่าน snapshot เต็มของงานเป็นระยะและรวมกับคิวที่ยังไม่ส่งอย่างถูกต้อง แล้ววัดต้นทุน DB อีกครั้ง เป็นทางแก้ขนาดเล็กที่ไม่ต้องสร้างระบบ sync ใหม่ หากจะคง incremental polling ให้ใช้ revision ที่เพิ่มในธุรกรรมการเขียนและสัมพันธ์กับ snapshot จริง การย้าย `Date.now()` ไปก่อน SELECT อย่างเดียวแก้รูปแบบที่สองไม่ได้

**เกณฑ์ผ่าน:** ทั้งสองลำดับข้างต้นต้องเห็นรายการในการ sync รอบถัดไปโดยไม่ต้องรีโหลดหน้า และการ refresh ต้องไม่ทับรายการที่ยังอยู่ใน outbox

### N04 — P1: ให้คะแนนพร้อมรับงานครั้งแรกเปลี่ยนเวลาส่งและทำให้เด็กถูกนับส่งช้าผิด

**ทำซ้ำได้:** งานกำหนดส่งวันที่ 29 ก.ย. คำขอให้คะแนนเริ่มโดยยังไม่เห็นการส่งและหยุดก่อน batch ระหว่างนั้นคำขอรับงานของเด็กที่ส่งก่อนเที่ยงคืนบันทึกสำเร็จ แล้วปล่อยคำขอให้คะแนนซึ่งมีเวลาเหตุการณ์หลังเที่ยงคืน

**ผลจริง:** แถวที่รับงานแล้วมี `submitted_at=1790701190005, late=0` หลังให้คะแนน 8 เปลี่ยนเป็น `submitted_at=1790701200005, late=1` ทั้งสองคำขอตอบ `ok` เด็กที่ส่งทันเวลากลายเป็นส่งช้า ทั้งที่เปลี่ยนเพียงคะแนน

**สาเหตุ:** `wasSubmitted`, `submitted_at` และ `late` คำนวณจากแถวที่อ่านก่อนธุรกรรม SQL upsert ทับค่าทั้งหมดด้วย `excluded` แม้ขณะเขียนจะมีแถว submitted อยู่แล้ว

จุดแก้: [คำนวณเวลาส่งจาก before](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/worker/routes/submissions.ts:271), [SQL ทับเวลาส่งและ late](C:/Users/User/Desktop/teacher/.audit/ce751ea/teacher/worker/routes/submissions.ts:126)

**แนวแก้:** สำหรับการแก้คะแนน ให้รักษาเวลาส่ง/late ของแถว submitted จริงขณะเขียนภายในธุรกรรม กำหนดใหม่เฉพาะการเปลี่ยนเข้ารัฐ submitted ครั้งแรกตามกติกาของระบบ และให้ ACK/audit ใช้แถวที่เขียนจริง ควรครอบคลุม bulk ให้คะแนนด้วย เพราะใช้ before ที่อ่านล่วงหน้าเหมือนกัน

**เกณฑ์ผ่าน:** คะแนนเปลี่ยนเป็น 8 แต่เวลาส่งเดิมและ `late=0` ต้องคงอยู่ ทดสอบทั้งส่งทันเวลา/ส่งช้า/ยกเลิกแล้วส่งใหม่ และลำดับคำขอจากสองเครื่อง

## ความพร้อมหลังบ้านและขอบเขตการใช้งาน

การป้องกัน epoch/idempotency, การเขียนเป็น batch, การตรวจข้อมูล, การสำรองที่เช็ค fingerprint, การกู้คืนแบบ staging และการทดสอบปริมาณข้อมูลดีขึ้นชัดเจน ชุด API ผ่านในการตรวจนี้ อ้างอิงแนวทาง platform จาก [Cloudflare Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/) และการทำธุรกรรมของ [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) แต่ transaction ทำให้เขียนพร้อมกันแบบ atomic ไม่ได้ทำให้ before ที่อ่านไว้นอก transaction สดขึ้นเอง ดังที่ N02/N04 แสดง

ด้านบัญชีพบ session cookie แบบ HttpOnly/Secure/SameSite Strict, จำกัดการลองรหัสผ่าน, SESSION_PEPPER ที่ขาดแล้วปฏิเสธการใช้งาน และมีการออกจากระบบรายอุปกรณ์ อย่างไรก็ตามรุ่นนี้ออกแบบสำหรับบัญชีครูเดียว ไม่ใช่ระบบหลายครูที่แบ่งสิทธิ์รายห้อง การเปลี่ยนรหัสผ่านยังไม่ยกเลิก session เครื่องอื่น ตามที่ STATUS ระบุไว้ ถ้าต้องการขั้นตอนจัดการเครื่องหายที่สั้นลง ค่อยเพิ่ม “ออกจากระบบทุกเครื่อง” ภายหลัง; ตอนนี้ใช้การออกจากระบบรายเครื่องได้

เรื่องประวัติเด็กย้ายห้อง/ซ้ำชั้นยังไม่ได้ทำ หากโรงเรียนต้องการให้รายงานย้อนหลังยึดห้องในวันที่เกิดรายการ ต้องกำหนดนโยบายและทดสอบกรณีนั้นก่อนนำไปใช้ข้ามเทอม ไม่ควรถือว่าชุดทดสอบหนึ่งเทอมยืนยันรายงานย้อนหลังทุกกรณีแล้ว

## แผนรอบสุดท้ายที่เสนอ

| ลำดับ | งาน | เกณฑ์ปิดงาน |
|---|---|---|
| 1 — ต้องแก้ | N01/N02/N04: guard ของ undo, before จริงของ audit และเวลาส่ง/late ที่ไม่เปลี่ยนจากการให้คะแนน | เพิ่ม regression ที่จับผลผิดได้ก่อนแก้ แล้วกรณีทำซ้ำต้องผ่านทั้งหมด ไม่มีคะแนน/เวลาส่งเสียจากคำขอพร้อมกัน |
| 2 — ต้องแก้ | N03: sync โดย snapshot หรือ commit revision; แก้ข้อทดสอบ redirect ให้ถูก environment | ทดสอบทั้งช่องว่าง read→response และ write เริ่มก่อน commit; คิว local ไม่ถูกทับ; `npm test`, typecheck และ build ผ่านทั้งชุด |
| 3 — ตรวจ deployment จริง | ยืนยัน URL/รุ่น deploy, DB/schema/secrets ผ่าน health; ตรวจ header ของเว็บจริงและดู runtime error/CPU/DB cost ระหว่างทดลอง | production configuration ตรงรุ่นและไม่มี error ที่ local ตรวจไม่เห็น; ZIP ปัจจุบันที่มี database_id ตัวอย่างไม่ใช่หลักฐานว่าขั้นนี้ผ่าน |
| 4 — ทดลองหนึ่งห้อง | ใช้ iPad/Safari หรือ Android และเครื่องยิง/เครื่องพิมพ์จริงของครู ตาม TRIAL.md ที่มีแล้ว; ทดลอง Wi-Fi ขาด, เปิดใหม่, ส่งคิว, ใช้สองเครื่อง, รับงาน/ให้คะแนน/เช็คชื่อ และเทียบกระดาษกับ Excel | รายชื่อนักเรียน จำนวนส่งงาน คะแนน สถานะสาย/เช็คชื่อ และยอดรวมตรงกันทุกจุด คิวต้องส่งครบ ไม่มีรายการหายหรือซ้ำ |
| 5 — ซ้อมกู้คืน | ใช้ไฟล์สำรองของโรงเรียนบนฐานทดสอบที่แยกจริง แล้วเทียบทุกยอด | สำรองกู้ได้และค่าที่ใช้ตัดสินคะแนนตรงกับต้นฉบับ; ซ้อมโดยไม่แทนข้อมูล production |

เมื่อ 1–5 ผ่าน สามารถหยุดเพิ่มฟีเจอร์และเริ่มใช้ในขอบเขตที่ทดลองผ่านแล้ว ไม่ต้องรื้อ UI เพื่อให้รู้สึกว่าระบบสมบูรณ์ขึ้น

**ยังไม่ยืนยันในรอบนี้:** URL production, รุ่นที่ deploy จริง, secrets/bindings/โควตา/CPU จริง, Safari/iPad จริง, กล้องและเครื่องยิงจริง, QR ที่พิมพ์ออกมาจริง และการทดลองในห้องเรียนจริง ชุด browser E2E ที่แนบมาใน ZIP มีอยู่ แต่ไม่ได้รันชุดนั้นซ้ำทั้งหมดในรอบนี้ การทดสอบ UI รอบนี้ทำผ่านเบราว์เซอร์โดยตรงกับ fixture ที่แยกข้อมูล

การตรวจนี้สร้างเฉพาะรายงาน ภาพหลักฐาน และ script ทดสอบ ยังไม่ได้แก้ source ระบบหรือ deploy อะไร
