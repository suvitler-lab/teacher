## ความพร้อมด้านระบบ

### ข้อมูลและการทำงานหลายเครื่อง

ต้องผ่าน B01–B05 ก่อน จุดร่วมคือ “ตรวจข้อมูลก่อนเขียน” ยังไม่เท่ากับ “ตรวจและเขียนในธุรกรรมเดียวกัน” รวมถึงผลสำเร็จต้องอิงค่าที่บันทึกจริง ไม่ใช่ค่าที่ตั้งใจจะบันทึก

### ออฟไลน์และ PWA

- คิวและ draft พัฒนาขึ้นมาก แต่ยังต้องทดสอบเปิดครั้งแรก→ปิดเน็ต→reload รวมถึงปิดแอป/เปิดใหม่และ session หมดอายุ
- จากโค้ด `sw.js` ยังไม่มี precache ตอน install และลงทะเบียนหลัง window load จึงยังไม่มีหลักประกันว่า shell/assets พร้อมออฟไลน์หลังการเปิดครั้งแรก ประเด็นนี้เป็นความเสี่ยงจากการตรวจโค้ด ยังไม่ได้ยืนยันการล้มเหลวใน browser จริงรอบนี้
- ควรมีสถานะ “พร้อมใช้ออฟไลน์” หลังเตรียมไฟล์จำเป็นเสร็จ และแจ้งเมื่อมีเวอร์ชันใหม่ โดยไม่ทิ้งคิวค้าง
- ข้อความติดตั้ง PWA/เก็บถาวรไม่ควรรับประกันว่าข้อมูลในเครื่องจะไม่มีวันถูกลบ ควรสื่อว่าเป็นการลดความเสี่ยงและยังต้องส่งข้อมูลขึ้นระบบ

### สำรองข้อมูลและการกู้คืน

- Restore แบบ staging/transaction ดีขึ้นและ tests ครอบคลุมกรณียกเลิก/อัปโหลดไม่ครบแล้ว
- Backup อ่านหลายตารางหลายคำขอ ยังไม่มี snapshot เดียว หากอีกเครื่องแก้ข้อมูลระหว่างสำรอง อาจได้ข้อมูลคนละช่วงเวลา: ควรเพิ่มการตรวจ revision หรือกลไก snapshot พร้อมทดสอบกรณีมีการเขียนระหว่าง backup ประเด็นนี้ยังเป็นข้อเสี่ยงจากโค้ด ไม่รวมในรายการบั๊กที่จำลองยืนยันแล้ว
- ก่อนเปิดจริง ต้องทดลองกู้คืนไปฐานข้อมูลทดสอบแยกและเทียบจำนวน/คะแนน/เช็คชื่อ ไม่เพียงดูว่าดาวน์โหลด JSON สำเร็จ

### ความปลอดภัยและการดูแลระบบ

- มี auth, cookie HttpOnly/Secure/SameSite, same-origin write guard, validation, จำกัดการลองรหัสผ่าน และประวัติการแก้ไข
- ควร fail fast เมื่อ production ไม่ได้ตั้ง SESSION_PEPPER แทนการใช้ค่า fallback; รอบนี้ไม่อ่านค่าความลับจริงและไม่ยืนยันค่าบน Cloudflare
- พิจารณาปุ่ม “ออกจากระบบทุกเครื่อง” และตัวเลือกยกเลิก session อื่นเมื่อเปลี่ยนรหัสผ่าน เพราะ route เปลี่ยนรหัสปัจจุบันไม่ได้ยกเลิก session เดิม
- ถ้าจะให้หลายครูใช้ร่วมกัน ต้องเพิ่มบัญชี/สิทธิ์และ audit ที่ระบุตัวบุคคล โครงปัจจุบันเป็นบัญชีครูเดียวกับชื่ออุปกรณ์
- มีข้อมูลนักเรียนและ QR ในไฟล์สำรอง ควรกำหนดที่เก็บและคนที่เข้าถึงได้ รวมทั้งระยะเวลาเก็บข้อมูลให้ตรงกับการใช้งานจริง

### ประสิทธิภาพและการนำขึ้นใช้งาน

- Bundle หลักประมาณ 272.55 kB (gzip 80.7 kB), CSS 257.61 kB (gzip 51.3 kB), icon font woff2 ประมาณ 504 kB; ExcelJS แยกโหลดประมาณ 940 kB จึงควรลดชุด icon ก่อนงานปรับแต่งเล็กน้อย
- ยังไม่ได้วัด Core Web Vitals/การใช้ CPU กล้องจริง จึงไม่สรุปว่าเร็วเพียงพอทุกเครื่อง
- `wrangler.jsonc` ยังมี database_id เป็น placeholder ต้องกำหนดฐาน production, migrations และ secrets ก่อน deploy
- ยังไม่ได้ตรวจหรือ deploy Cloudflare production; การ build ผ่านไม่ใช่หลักฐานว่า configuration บนบริการจริงพร้อม
- ก่อนใช้จริงควรมีรุ่นที่ย้อนกลับได้, วิธีรับมือ schema mismatch/ฐานข้อมูลใช้ไม่ได้, บันทึกเหตุขัดข้อง และการแจ้งเมื่อบันทึกไม่สำเร็จที่ไม่กลืน error เงียบ

## แผนรอบถัดไปพร้อมเกณฑ์ส่งงาน

### รอบ 1 — ปิดความเสี่ยงข้อมูล

1. ทำ transaction guard สำหรับ epoch, คะแนนเต็ม, สถานะงานและความสัมพันธ์ห้องให้สอดคล้องกับ mutation; แก้ B01/B05/B07/B08
2. ให้ response และ audit อิงผลเขียนจริง; แก้ B03/B04 และตรวจ bulk/undo ด้วย
3. แยก cache และคำตอบสแกนตาม assignment/session; แก้ B02
4. ย้ายกรณีจากสคริปต์ audit ไปเป็น regression tests ที่คุมจังหวะ concurrent request ได้

**ส่งงานเมื่อ:** ทำลำดับเหตุการณ์ทั้ง 7 ข้อได้โดยข้อมูล/หน้าจอ/audit ตรงกัน, ไม่มีคะแนนเกินเต็ม, ไม่มีรายการเก่าเขียนหลัง restore, ชุด 226 tests เดิมยังผ่าน

### รอบ 2 — ใช้งานผ่านกล้องและหน้าจอได้ครบ

1. แก้ CSP/WASM และข้อความผิดพลาดกล้อง (B06)
2. แก้ CSS ของการ์ดเช็คชื่อ/แถบวัน/การ์ดเลือกงาน (B09/B10), checkbox และปุ่ม Settings ที่หดตัว
3. แสดงชื่อเต็มงานบนมือถือ, ขยายจุดแตะ, เพิ่ม label ของปุ่มที่ระบุเฉพาะตัวเลข
4. ทำ Settings ที่ขาดจากแผนเดิม: แก้ชื่อ/สี/ลำดับ/คะแนนเริ่มต้น พร้อมแสดงปีของห้องให้ชัด

**ส่งงานเมื่อ:** เดินงานเช็คชื่อ→รับงาน→ให้คะแนน→รายงานบน 360/390/430 px และคอมพิวเตอร์ได้, ไม่มีชื่อถูกยุบหรือหน้าล้น, ทดสอบ QR ด้วยกล้อง/เครื่องยิงและคีย์บอร์ดไทยบนอุปกรณ์ที่จะใช้จริง

### รอบ 3 — ความต่อเนื่องก่อนเปิดเทอม/เปิดระบบ

1. เตรียม offline shell/assets และสถานะพร้อมใช้; ทดสอบตัดเน็ต/ปิดแอป/เปิดใหม่/เข้าสู่ระบบใหม่
2. ทำ backup ให้ตรวจความสอดคล้องและทดสอบ restore แยกฐาน พร้อมตรวจรายการค้างจากเครื่องอื่น
3. ตกลงนโยบายเด็กย้ายห้อง/ซ้ำชั้น/ออกกลางเทอม ก่อนเพิ่มประวัติสมาชิกห้อง หากเป็นกรณีที่โรงเรียนต้องใช้
4. กำหนด production configuration, ทดสอบ migrations/ย้อนรุ่น และทดสอบข้อมูลขนาดใกล้เคียงใช้งานจริง

**ส่งงานเมื่อ:** คะแนน เช็คชื่อ และตัวเลขรายงานตรงกันทั้ง UI/Excel/ข้อมูลที่กู้คืน; ไม่มีร่างหายหลังเปิดแอปใหม่; deployment ที่จะใช้จริงผ่านการทดลอง

### รอบ 4 — ทดลองในห้องเรียนก่อนขยาย

ทดลองหนึ่งห้องด้วยขั้นตอนงานครบวัน ตั้งแต่เช็คชื่อ รับงาน แก้คะแนน เน็ตหลุด จนถึงรายงานท้ายวัน เทียบกับบันทึกควบคู่และเก็บจุดที่ครูต้องกดซ้ำหรือไม่เข้าใจ เมื่อผลตรงกันจึงขยายไปทุกห้อง
