## วิธีที่ใช้ปิดความเสี่ยงข้อมูล (B01/B04/B05)

ตรวจก่อนเขียนอย่างเดียวไม่พอ ต้องตรวจซ้ำในธุรกรรมเดียวกับการเขียน (D1 `batch` = ธุรกรรมเดียว)

- `worker/lib/guard.ts` — `abortIf` (ทำให้ทั้ง batch ล้มและย้อนกลับ, ใช้ทริก `json('…')` เดียวกับ restore/เช็คชื่อที่มีอยู่) และ `batchAtEpoch`
- `app.ts` เก็บ epoch ตอนเริ่มคำขอเขียนทุกคำขอ; route เขียนข้อมูลเช็คซ้ำใน batch
- คะแนน/bulk: เงื่อนไขเดียวกัน (`stillValid` ใน `submissions.ts`) อยู่ทั้งที่ `INSERT … WHERE` ของ submission **และ** ของ audit — audit ลงได้ก็ต่อเมื่อแถวถูกเขียนจริง (audit ไปก่อน upsert เพื่อให้ทั้งสองอ่านสถานะ "ก่อน" เดียวกัน)
- คำตอบของ `/api/submissions/batch` ดูจาก audit ที่ลงจริง: ลงแล้ว = `ok`; ไม่ลง = อธิบายจากข้อมูลตอนนี้ (`epoch_changed` / `full_score_changed` / `assignment_closed` / `not_in_class` / `superseded`)
- แก้งาน (`/api/assignments`): guard "ลดคะแนนเต็มต่ำกว่าคะแนนที่มี" อยู่ในธุรกรรม; bulk-undo กันการกดซ้ำและแก้ระหว่างทางด้วย guard ใน batch

ข้อจำกัดที่ยังมี: `before` ใน audit มาจากที่อ่านตอนเริ่มคำขอ ถ้ามีเครื่องอื่นเขียนคั่นและเวลาเก่ากว่า ค่า `before` อาจไม่ใช่ค่าล่าสุดจริง (ค่า `after` และข้อมูลในตารางถูกต้องเสมอ)

## งานเสริมในรอบเดียวกัน (รอบ 2 ของแผน)

- ตั้งค่า ▸ พื้นฐาน: แก้ชื่อ/สี/คะแนนเต็มเริ่มต้น/เป็นการสอบ และเลื่อนลำดับ ห้อง/วิชา/ประเภทงาน; แสดงปีการศึกษาของห้องทุกห้อง — `test/unit/catalog-editor.test.tsx`
- จอสัมผัส (`pointer: coarse`): ปุ่มสูงอย่างน้อย 40px (ยกเว้น chip ในบรรทัดและลิงก์หัวการ์ดอย่าง "สมุดคะแนน ›"), ปุ่มคะแนนในมุมมองมือถือ 44px — จอคอมพิวเตอร์คงความหนาแน่นเดิม
- สมุดคะแนนมือถือ: แสดงชื่อเต็มของงานที่เลือกเหนือรายชื่อ; หน้าตั้งรอบสแกนสรุป "รอบนี้: …" เต็มชื่อก่อนกดเริ่ม
- ปุ่มแบบการ์ดที่เคยถูกบังคับสูง 38px ทั้งกลุ่ม (หน้าแรก `hm-follow`/`hm-action`, รายงาน `rp-follow`, ปุ่ม "ขอเก็บถาวร") แก้ให้สูงตามเนื้อหา

การตรวจหน้าจอใช้ตัวกวาดทุกเมนู (8 หน้า) × 360/390/430px หาปุ่มที่ข้อความถูกตัด, หน้าล้นแนวนอน และจุดแตะที่เล็กกว่า 32px: ที่ 390px ก่อนแก้พบปุ่มที่ข้อความถูกตัด 17 จุด (หน้าแรก 7, เช็คชื่อ 3, รายงาน 6, ตั้งค่า 1) และจุดแตะเล็กหลายสิบจุด หลังแก้เหลือ 0 ทั้งสองอย่างที่ทั้งสามความกว้าง (จำลองจอสัมผัสด้วย Chromium ไม่ใช่เครื่องจริง)

## รอบ 4 — เตรียมการทดลองในห้องเรียนจริง (ยังไม่ได้ทดลอง)

**การทดลองในห้องเรียนจริงยังไม่ได้ทำ** — ต้องใช้เครื่องจริง เด็กจริง และ wifi ของโรงเรียน ซึ่งผมไม่มี สิ่งที่ทำได้คือตรวจทุกอย่างที่ตรวจได้โดยไม่มีอุปกรณ์
และเตรียมชุดทดลองให้ครู ขั้นตอนและเกณฑ์ผ่านอยู่ใน [`docs/TRIAL.md`](../TRIAL.md) แบบบันทึกที่พิมพ์ได้อยู่ใน `docs/trial/TRIAL-LOG.md`

| เรื่อง | สถานะ | หลักฐาน |

### สิ่งที่พบและแก้ระหว่างเตรียม (ทุกข้อพบจากการรันในเบราว์เซอร์จริง ไม่ใช่จากการอ่านโค้ด)

| ปัญหา | ผล | แก้ |
|---|---|---|
| ฟอนต์ถูกฝังเป็น `data:` ในไฟล์ CSS | CSP ของแอป (ไม่มี `font-src`) **ปฏิเสธฟอนต์ทั้งหมด** — หน้าจอถอยไปใช้ฟอนต์ระบบโดยไม่มีข้อความเตือน | `vite.config.ts` ไม่ฝังฟอนต์; `preflight --built` ล้มถ้าเจอ `url(data:font…)` อีก (มี test) |

**ข้อจำกัดของสิ่งที่วัดได้ (สำคัญ):** การอ่าน QR ในรอบนี้ใช้ภาพสังเคราะห์ที่คมชัด ไม่เบลอ ไม่มีแสงสะท้อน ไม่มีสัญญาณรบกวน — อ่านได้แม้ QR กว้างแค่ ~4% ของภาพ
ซึ่งง่ายกว่ากล้องจริงมาก **ห้ามใช้เป็นหลักประกันว่าสติกเกอร์ 40 ดวง (QR ≈ 14 มม.) อ่านได้** แอปยังไม่ขอความละเอียดกล้องสูงกว่าค่าเริ่มต้น
ยังไม่ได้แก้เรื่องนี้เพราะยังไม่เห็นปัญหาจริงบนเครื่องใด — ให้ตัดสินจากผลพิมพ์จริงตาม `TRIAL.md` §1

**สิ่งที่การทดลองต้องตัดสิน:** กล้องเครื่องจริงอ่านบัตรพิมพ์จริงได้ทุกดวงหรือไม่ (โดยเฉพาะ 40 ดวง/แผ่น), เครื่องยิงรุ่นที่ใช้ส่ง Enter ท้ายรหัสไหม,
Safari/iPad เก็บข้อมูลออฟไลน์ไว้ได้ตลอดวันไหม, wifi โรงเรียนหลุด/ค้างแล้วคิวส่งครบไหม, ครูจดกระดาษควบคู่ไปกับใช้แอปได้จริงไหม, และเกณฑ์ผ่านที่เสนอสมเหตุสมผลกับครูไหม

## ยังไม่ได้ทำ / ยังไม่ได้ยืนยัน

การทดลองในห้องเรียนจริงหนึ่งห้อง (รอบ 4 ในแผนเดิม) **ยังไม่ได้ทำ** (เตรียมชุดไว้แล้วข้างบน) และเรื่องต่อไปนี้ **ไม่ได้ตรวจ**:

- กล้อง/เครื่องยิง, **Safari/iPad จริง** (พฤติกรรม service worker/IndexedDB ของ Safari, การล้างข้อมูลเว็บ), งานพิมพ์บนเครื่องพิมพ์จริง — ต้องทดสอบบนอุปกรณ์ที่จะใช้จริง
  (ผลออฟไลน์ข้างบนวัดบน Chromium เท่านั้น)
- **Cloudflare production** — guard ใน batch, ตัวเลขแถวอ่าน/เขียน และคำสั่ง `wrangler rollback` / `d1 time-travel` ทดสอบบน D1 จำลองของ Miniflare หรือไม่ได้รันเลย;
  การนับโควตาจริงของ Cloudflare อาจต่างเล็กน้อย, `npm run check:health` ยังไม่เคยรันกับ deploy จริง
- `wrangler.jsonc` ยังเป็น `database_id` ตัวอย่าง — `npm run deploy` จะหยุดจนกว่าจะสร้างฐานข้อมูลจริง (ตั้งใจ)
- เปลี่ยนรหัสผ่านแล้วยังไม่ยกเลิก session ของเครื่องอื่น / ยังไม่มีปุ่ม "ออกจากระบบทุกเครื่อง" (ออกจากระบบทีละเครื่องได้จากหน้าตั้งค่า)
- อัปโหลด `.xlsx`, หน้าผู้ปกครอง, ประวัติสมาชิกห้อง (ย้ายห้อง/ซ้ำชั้น), การลบข้อมูลเก่าตามนโยบายเก็บข้อมูล
