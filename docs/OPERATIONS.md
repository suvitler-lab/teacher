# คู่มือปฏิบัติการ — deploy, ย้อนรุ่น, กู้ข้อมูล, แก้อาการ

สำหรับคนที่ดูแลระบบ (ปกติคือครูเจ้าของระบบ) ทุกคำสั่งรันที่โฟลเดอร์โปรเจกต์ ชื่อฐานข้อมูลคือ `kru-db`

> คำสั่งที่ขึ้นต้นด้วย `npx wrangler …` ต้องเข้าสู่ระบบ Cloudflare ก่อน (`npx wrangler login`) และ **ยังไม่ได้ทดสอบกับบัญชี Cloudflare จริง** —
> ตรวจชื่อคำสั่งกับ `npx wrangler <คำสั่ง> --help` ก่อนใช้ครั้งแรก ส่วนสคริปต์ `npm run …` ในโปรเจกต์นี้มี test คุมอยู่

## 1. Deploy ทุกครั้ง (checklist)

1. **สำรองข้อมูลก่อน** — ตั้งค่า → สำรองข้อมูล → ดาวน์โหลด (ถ้า `migrations/` มีไฟล์ใหม่ จำเป็นมาก)
2. `npm test` และ `npm run typecheck` ผ่าน
3. `npm run db:migrate:remote` ถ้ามีไฟล์ใหม่ใน `migrations/` — **ก่อน** deploy เสมอ
4. `npm run deploy` — สคริปต์นี้รัน `preflight` ก่อนและหลัง build ให้เอง และหยุดพร้อมบอกสาเหตุถ้า
   - `wrangler.jsonc` ยังเป็น `database_id` ตัวอย่าง
   - ไฟล์ migration เลขข้ามกัน หรือ schema ของ migration สุดท้ายไม่ตรงกับ `SCHEMA_VERSION` ของแอป
   - build ไม่ได้สร้างไฟล์ออฟไลน์ (`sw.js`) หรือ config สำหรับ deploy
5. **ตรวจหลัง deploy:** `npm run check:health -- https://<ชื่อ>.<subdomain>.workers.dev`
   ต้องขึ้น ✔ — ถ้าไม่ จะบอกเป็นภาษาคนว่าอะไรขาด (ฐานข้อมูลว่าง / schema ไม่ตรง / ยังไม่ตั้ง `SESSION_PEPPER`)
6. เปิดแอปบนมือถือ/แท็บเล็ตที่ใช้จริง 1 ครั้งตอนมีเน็ต → ตั้งค่า → ทั่วไป → **ใช้ออฟไลน์** ต้องขึ้น "พร้อม"
   (ครั้งแรกใช้เวลาโหลดไฟล์ราว 3 MB) — ถ้าขึ้น "ไม่พร้อม" ให้ต่อเน็ตแล้วเปิดแอปใหม่
7. เครื่องที่เปิดแอปค้างไว้จะเห็นแถบ **"มีเวอร์ชันใหม่"** เอง ไม่ถูกเปลี่ยนกลางคัน กดเมื่อสะดวก (งานที่ค้างส่งในเครื่องไม่หาย)

## 2. ความลับ (secrets)

| ชื่อ | ใช้ทำอะไร | หมายเหตุ |
|---|---|---|
| `SESSION_PEPPER` | ผสมเข้าไปในการเก็บรหัสผ่านครู | **ต้องตั้ง** — ไม่มีค่าเริ่มต้น ถ้าไม่ตั้งระบบปฏิเสธการตั้งรหัสผ่านและการเข้าสู่ระบบ (`config_missing`) สร้างค่าด้วย `openssl rand -base64 32` |
| `SETUP_CODE` | รหัสสำหรับตั้งรหัสผ่านครั้งแรก | ใช้ครั้งเดียวตอนสร้างบัญชี ตั้งให้เดายาก |

ตั้งด้วย `npx wrangler secret put SESSION_PEPPER` (พิมพ์ค่าเมื่อระบบถาม) — เก็บค่าไว้ในที่ปลอดภัยแยกจากไฟล์สำรอง

> **ห้ามเปลี่ยน `SESSION_PEPPER` หลังตั้งรหัสผ่านแล้ว** — รหัสผ่านเดิมจะตรวจไม่ผ่านอีก ต้องรีเซ็ตรหัสผ่าน (หัวข้อถัดไป)

## 3. ลืมรหัสผ่านครู / เปลี่ยน pepper — รีเซ็ตรหัสผ่าน

ข้อมูลนักเรียน คะแนน เช็คชื่อ **ไม่ถูกแตะ** (มี test ยืนยัน) เครื่องทุกเครื่องจะถูกให้เข้าสู่ระบบใหม่

```bash
npx wrangler d1 execute kru-db --remote --command "DELETE FROM teacher; DELETE FROM sessions; DELETE FROM login_attempts;"
```

จากนั้นเปิดแอป จะเข้าหน้าตั้งรหัสผ่านครั้งแรก ใส่ `SETUP_CODE` แล้วตั้งรหัสผ่านใหม่
คะแนนที่ค้างส่งในเครื่องต่าง ๆ ไม่หาย — จะส่งขึ้นระบบเองหลังเข้าสู่ระบบใหม่

การเข้าสู่ระบบ: ผิด 5 ครั้งใน 15 นาทีจะถูกพักชั่วคราว (ล้างได้ด้วยคำสั่งข้างบน) · session อยู่ได้ 30 วัน
ถ้าเครื่องหาย: ตั้งค่า → อุปกรณ์และรหัสผ่าน → ออกจากระบบเครื่องนั้น

## 4. ย้อนรุ่น (rollback)

**โค้ดกับฐานข้อมูลย้อนแยกกัน และ schema ย้อนกลับเองไม่ได้** (migration เพิ่มอย่างเดียว) — แอปเช็ค schema ทุกคำขอ
ถ้าโค้ดกับฐานข้อมูลคนละรุ่น จะตอบ `schema_mismatch` (503) และไม่แตะข้อมูล — ปลอดภัยแต่ใช้งานไม่ได้จนกว่าจะตรงกัน

| สถานการณ์ | ทำอย่างไร |
|---|---|
| รุ่นใหม่มีบั๊ก และ **ไม่มี** migration ใหม่ | ย้อนโค้ดได้เลย: `npx wrangler rollback` (หรือ Cloudflare dashboard → Workers → Deployments → Rollback) |
| รุ่นใหม่มีบั๊ก และ **มี** migration ใหม่ | อย่าย้อนโค้ดอย่างเดียว (จะ `schema_mismatch`) — **แก้ไปข้างหน้า**: แก้บั๊กแล้ว deploy รุ่นใหม่อีกครั้ง |
| ข้อมูลเสียหายจากรุ่นใหม่ | กู้จากไฟล์สำรอง (หัวข้อ 5) — แทนข้อมูลปัจจุบันทั้งชุด ข้อมูลหลังวันที่สำรองจะหาย |
| ข้อมูลเสียหายและไม่มีไฟล์สำรองที่ใช้ได้ | D1 Time Travel ย้อนได้ 7 วัน: `npx wrangler d1 time-travel info kru-db` ดูจุดที่ย้อนได้ แล้ว `npx wrangler d1 time-travel restore kru-db --timestamp=<เวลา>` — **ย้อนข้อมูลทั้งฐาน** ทุกอย่างหลังเวลานั้นหาย และต้องย้อนโค้ดให้ตรง schema ของเวลานั้นด้วย |

## 5. สำรองและกู้คืนข้อมูล

- สำรอง: ตั้งค่า → สำรองข้อมูล → ดาวน์โหลด ระบบอ่านข้อมูลหลายคำขอ แล้ว**ตรวจซ้ำว่าระหว่างอ่านไม่มีเครื่องอื่นบันทึก**
  ถ้ามี จะอ่านใหม่เองสูงสุด 3 รอบ และถ้ายังไม่นิ่งจะ **ไม่สร้างไฟล์** (แจ้งให้หยุดสแกน/เช็คชื่อสักครู่แล้วลองใหม่) —
  ไฟล์ที่ได้มาจึงเป็นภาพของ "เวลาเดียว" เสมอ
- **ความถี่ที่แนะนำ:** สัปดาห์ละครั้ง + ก่อนสิ้นเทอม/สิ้นปี + ก่อน deploy ที่มี migration
- **ไฟล์สำรองเป็นข้อมูลอ่อนไหว:** มีชื่อนักเรียน คะแนน และ QR token กับ PIN ของนักเรียน — เก็บในที่ที่คนอื่นเข้าไม่ได้ (ไม่ส่งผ่านกลุ่มแชท ไม่ฝากไว้ในเครื่องสาธารณะ)
  และลบชุดเก่าที่ไม่ต้องใช้แล้วตามนโยบายของโรงเรียน (ระยะเวลาเก็บต้องให้โรงเรียนกำหนด ระบบไม่ลบข้อมูลให้เอง)
- กู้คืน: ตั้งค่า → กู้คืน (ดูรายละเอียดใน README ส่วน "สำรองและกู้คืนข้อมูล")

### ซ้อมกู้คืนก่อนเปิดเทอม (restore drill)

ไฟล์สำรองที่ไม่เคยลองกู้ ไม่ใช่หลักประกัน ควรซ้อมอย่างน้อยปีละครั้งและก่อนเปิดเทอม **บนเครื่องทดสอบ ไม่ใช่ระบบจริง**:

1. `npm run db:migrate:local` แล้ว `npm run dev` (ฐานข้อมูล local แยกจากระบบจริง)
2. ตั้งรหัสผ่านตามหน้าจอ (ใช้ `.dev.vars` — คัดลอกจาก `.dev.vars.example`)
3. ตั้งค่า → กู้คืน → เลือกไฟล์สำรองล่าสุดของระบบจริง → กู้คืน
4. เทียบกับระบบจริง: จำนวนนักเรียน/งาน/ส่งงาน/เช็คชื่อที่หน้าตัวอย่างไฟล์ · คะแนนของงานหนึ่งที่รู้ค่า · ส่งออก Excel แล้วเทียบผลรวมคะแนน
5. ต้องตรงกันทุกตัวเลข ถ้าไม่ตรง — หยุด อย่าใช้ไฟล์ชุดนั้นเป็นสำรองเดียว แล้วแจ้งผู้พัฒนา

ระบบมี test อัตโนมัติของการซ้อมนี้ที่ขนาดโรงเรียนจริง (200 นักเรียน · คะแนน 8,000 รายการ · เช็คชื่อ 12,000 รายการ):
สำรอง → ทำลายข้อมูลทุกส่วน → กู้คืน → เทียบทุกแถวทุกคอลัมน์ (`test/api/backup-consistency.test.ts`) — ไม่ได้แทนการซ้อมกับไฟล์จริงของคุณ

## 6. แก้อาการ

| อาการ | สาเหตุที่พบบ่อย | แก้ |
|---|---|---|
| ทุกหน้าตอบ `schema_mismatch` (503) | deploy โค้ดใหม่แต่ยังไม่ migrate ฐานข้อมูล | `npm run db:migrate:remote` |
| เข้าสู่ระบบ/ตั้งรหัสผ่านไม่ได้ ขึ้น `config_missing` | ยังไม่ได้ตั้ง `SESSION_PEPPER` | `npx wrangler secret put SESSION_PEPPER` (ถ้าเคยมีบัญชีอยู่แล้ว ดูหัวข้อ 3) |
| `npm run deploy` หยุดที่ preflight | ดูข้อความใต้ ✘ — บอกสิ่งที่ต้องแก้ | ตามข้อความ |
| ตั้งค่าขึ้น "ล็อกจากการกู้คืนครั้งก่อนที่ไม่จบ" | กู้คืนค้างกลางทาง | ตั้งค่า → สำรองข้อมูล → **ปลดล็อก** (ข้อมูลเดิมไม่ถูกเปลี่ยนเพราะกู้คืนสลับเข้าในธุรกรรมเดียว) |
| แอปหมุนโหลดนานตอนเปิด | wifi ต่อติดแต่ไม่ไหล | รอไม่เกิน ~8 วินาที แอปจะเปิดจากข้อมูลที่เก็บไว้เอง แล้วสลับเป็นข้อมูลจริงทันทีที่เซิร์ฟเวอร์ตอบ |
| ตั้งค่า → ใช้ออฟไลน์ ขึ้น "ไม่พร้อม/ไม่รองรับ" | ยังโหลดไฟล์ไม่ครบ / เปิดผ่านที่อยู่ที่ไม่ใช่ https / โหมดพัฒนา | เปิดผ่านลิงก์ `https://` ของระบบตอนมีเน็ต แล้วเปิดแอปใหม่ |
| มี "รอส่ง" ค้างในเครื่องหลายวัน | ไม่ได้ต่อเน็ต หรือเข้าสู่ระบบหมดอายุ | ต่อเน็ตแล้วเปิดแอป (ถ้าถามรหัสผ่านให้ใส่ — งานที่ค้างไม่หาย) |
| คำสั่ง SQL ค้นชื่อภาษาไทยด้วย `LIKE '%…%'` แล้วขึ้น `LIKE or GLOB pattern too complex` | D1 จำกัดรูปแบบ `LIKE` ที่ 50 ไบต์ และภาษาไทยตัวละ 3 ไบต์ | ใช้ `instr(คอลัมน์, 'คำ')` แทน |

## 7. ขีดจำกัดของแพ็กเกจฟรี (ที่การออกแบบต้องเคารพ)

ตัวเลขโดยประมาณ ณ เวลาที่เขียน — ตรวจหน้า Cloudflare dashboard ก่อนพึ่งพา:
Workers Free ใช้ CPU ได้ราว **10 ms ต่อคำขอ** และสั่งฐานข้อมูลได้ราว **50 คำสั่งต่อคำขอ**; D1 Free อ่านได้ราว **5 ล้านแถว** และเขียนได้ราว **100,000 แถวต่อวัน** (นับแถวของดัชนีด้วย)

**ที่วัดได้จริง** (ชุดข้อมูล 200 นักเรียน · 40 งาน · คะแนน 8,000 · เช็คชื่อ 12,000 — `test/api/volume.test.ts` คุมงบเหล่านี้ไว้):

| การทำงาน | คำสั่ง | แถวอ่าน | แถวเขียน |
|---|---:|---:|---:|
| สแกน 1 คน | 12 | 53 | 9 |
| สแกน 50 คนในคำขอเดียว (คิวออฟไลน์) | 12 | ~2,900 | ~400 |
| ทั้งห้อง: ให้เต็ม / ล้าง / ยกเลิกการล้าง | 13–14 | ~1,800 / ~2,100 / ~700 | ~300 |
| เช็คชื่อ 1 ห้อง (40 คน) | 15 | ~530 | ~360 |
| หน้าแรก (dashboard) | 10 | ~17,700 | 0 |
| สมุดคะแนน 1 ห้อง / รายงาน 1 ห้อง | 8 / 10 | ~3,800 / ~6,300 | 0 |
| สำรองข้อมูลทั้งฐาน (~21,000 แถว = ~51 คำขอ หน้าละ 500 แถว + ตรวจความสอดคล้อง 2 ครั้ง) | ~4 ต่อคำขอ | ~63,000 (ข้อมูล ~21,000 + ตรวจ ~42,000) | 0 |
| **กู้คืนเต็มชุด (ขั้นสลับข้อมูล)** | **38** | ~63,000 | **~92,000** |

ข้อควรรู้:
- **การกู้คืนเต็มชุดกินโควตาเขียนเกือบทั้งวัน** — ทำนอกเวลาเรียน ไม่ทำซ้ำในวันเดียวกัน และอย่าทำในวันที่ใช้งานหนัก ถ้าโควตาหมดกลางทาง ธุรกรรมล้มและย้อนกลับ (ข้อมูลเดิมไม่เสีย)
  แต่การบันทึกอื่น ๆ ของวันนั้นจะเขียนไม่ได้จนโควตารีเซ็ต (เที่ยงคืน UTC)
- **ถ้าโรงเรียนใหญ่กว่านี้** (หลายเท่า) ให้คิดเรื่องแพ็กเกจเสียเงิน หรือแบ่งฐานข้อมูลรายปีการศึกษา — ตัวเลขข้างบนโตตามจำนวนแถว
- ที่ผ่านมาคำสั่งแบบ `JOIN json_each(?1) j ON j.value = ตาราง.คอลัมน์` ทำให้หน้าแรกอ่านราว 330,000 แถวต่อครั้งและสแกนหนึ่งคนอ่านราว 16,000 แถว
  (เปิดหน้าแรกไม่กี่สิบครั้งก็หมดโควตาอ่านรายวัน) — แก้เป็น `WHERE คอลัมน์ IN (SELECT value FROM json_each(?1))` แล้ว **อย่าเขียนกลับเป็นรูปเดิม** (test งบจะล้ม)
- การแบ่งหน้าสำรองข้อมูลใช้ `rowid` ("500 แถวถัดจากแถวนี้") ไม่ใช่ `OFFSET` — แบบ OFFSET ต้องอ่านแล้วทิ้งแถวก่อนหน้าทุกหน้า ต้นทุนรวมเป็นกำลังสอง
  (เคยอ่าน ~239,000 แถวเพื่อสำรอง ~20,800 แถว) อย่าเปลี่ยนกลับ
- การสำรองอ่านทีละหน้า (500 แถว) แทนที่จะอ่านทั้งฐานในคำขอเดียว, การกู้คืนแบ่งเป็นหลายคำขอแล้วสลับเข้าในชุดคำสั่งเดียว (38 คำสั่ง),
  และงานเขียนหลายแถว (สแกนคิว, ทั้งห้อง) ใช้ JSON ก้อนเดียวต่อหนึ่งคำสั่ง — อย่าเปลี่ยนเป็นหนึ่งคำสั่งต่อแถว (เกินเพดานคำสั่งต่อคำขอ)

## 8. ทดสอบก่อนปล่อยเครื่องจริง

- `npm test` — ชุดทดสอบหลัก (API บน D1 จำลอง + หน้าจอ)
- `npm run build && npm run e2e:offline` — เปิดเบราว์เซอร์จริง (Chromium) ทดสอบการใช้ออฟไลน์ครบวงจรบนเซิร์ฟเวอร์ทดสอบที่ใช้ข้อมูลสมมติ:
  เปิดครั้งแรก → ตัดเน็ต (เซิร์ฟเวอร์ตัดการเชื่อมต่อจริง) → reload → สแกนเข้าคิว → ออนไลน์แล้วส่ง · session หมดอายุ · ปิดแอปเปิดใหม่ · เวอร์ชันใหม่ · เน็ตค้าง
  ต้องมี Playwright + Chromium ในเครื่อง (`npm i -g playwright && npx playwright install chromium`)
- **สิ่งที่ยังต้องทดสอบด้วยมือบนอุปกรณ์จริง:** กล้อง/เครื่องยิง QR, Safari บน iPad/iPhone (การล้างข้อมูลเว็บ, เพิ่มลงหน้าจอโฮม), งานพิมพ์สติกเกอร์จากเครื่องพิมพ์ที่จะใช้
