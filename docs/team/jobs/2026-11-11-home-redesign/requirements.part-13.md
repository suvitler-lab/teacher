## Q-A วิธีรับรอบนี้ (R-3901, R-3905)

**หลักฐาน**
- BR-14 เขียนว่านับ "`scan_session_id` = รอบนี้ ตาม `method`" และมีตัวอย่าง grid 1 · แต่ grid เกิดจากสมุดคะแนนเท่านั้น (Gradebook.tsx:299,349 ส่ง `scanSessionId:"grid"`) จึงไม่เคยตรงกับรอบสแกน → "แตะตาราง" ในตัวอย่างเกิดจริงไม่ได้ (BR เขียนขัดกันเอง)
- ผังที่นั่งในหน้าสแกนเรียก `commitStudent(st,"manual")` (ScanView.tsx:335) → server เก็บ manual
- โหมดกรอกทีละคน: op ใส่คะแนนใช้ method "manual" และ server เขียนทับ method ของแถว → ack แล้ว "เครื่องยิง 24" กลายเป็น "พิมพ์ 24"
- ที่มาของคำว่า "แตะตาราง" = ux-scan P1 "ใครรับด้วยการแตะมือ" (แตะช่องตาราง/สมุด) · P2 ต้องการสรุป "วิธีที่ครูรับงาน"

**คำตัดสิน:** "รอบนี้: …" = **วิธีที่ครูใช้รับงานตอนทำรายการในรอบนี้ ตามที่เครื่องรู้** ไม่ใช่ method ที่ server เก็บในแถว เพราะ method ใน server เปลี่ยนได้ตามการกระทำถัดมา (ใส่คะแนน) ซึ่งไม่ใช่วิธีรับ · ตัวเลขต้องคงที่ก่อน/หลังส่งขึ้นระบบ (หลักเดียวกับ BR-13 "ตัวเลขคงที่หลัง sync")

**แก้ที่ client เท่านั้น (ไม่ต้องเปลี่ยนสัญญา/op/worker):** ไม่ต้องเปลี่ยนสัญญา — op ยังส่ง method เดิมทุกประการ (manual สำหรับแตะผัง)

**BR-14 ข้อความใหม่ (แทนประโยค "วิธีรับรอบนี้")**
- นับนักเรียนที่รับ **ในรอบนี้บนเครื่องนี้** แต่ละคน 1 วิธี = วิธีของการรับครั้งแรกที่ทำให้เป็น "ส่งแล้ว" ในรอบนั้น · ใส่คะแนนทีหลังหรือ ack จากเซิร์ฟเวอร์ **ไม่เปลี่ยนวิธี**
- วิธี: ยิง HID = "เครื่องยิง" · กล้อง = "กล้อง" · พิมพ์เลขที่ในช่องรับเลข/ตอบการ์ดถาม = "พิมพ์" · **แตะช่องในผังที่นั่งของหน้าสแกน = "แตะตาราง"** (ใหม่ ติดป้ายในเครื่อง ไม่ส่งขึ้นระบบ) · ไม่ทราบ → ไม่นับ ไม่มีไอคอน
- เลิกทำ/ยกเลิกการส่ง → ถอนออก · รับซ้ำหลังยกเลิก → นับตามวิธีใหม่
- แถวที่ server มีแต่เครื่องไม่เคยเห็นการรับในรอบนี้ (เปิดแอปใหม่กลางรอบ/เครื่องอื่นส่ง): ใช้ method ที่ server เก็บถ้า `scan_session_id` ตรงรอบ (สำรอง · แตะตารางจะขึ้นเป็น "พิมพ์")
- การรับจากสมุดคะแนน (method grid, session "grid") **ไม่เข้ารอบสแกน** (A8 เดิมคงอยู่ เพิ่ม: grid ในสรุปรอบมาจากการแตะผังหน้าสแกนเท่านั้น)

**ตัวอย่าง (QA ใช้ได้)** โหมดกรอกทีละคน: ยิงบัตร 24 คน (HID) แล้วใส่คะแนนทั้ง 24 → ก่อนและหลัง ack = "รอบนี้: เครื่องยิง 24" · ยิง 16 + กล้อง 6 + พิมพ์เลข 1 + แตะผัง 1 → "เครื่องยิง 16 · กล้อง 6 · พิมพ์ 1 · แตะตาราง 1" (ตรงตัวอย่าง BR-14 เดิม) · ออฟไลน์ตั้งแต่ต้นแล้วใส่คะแนน → ยังเป็น "เครื่องยิง" · เลิกทำคนที่แตะผัง → "แตะตาราง" หาย (0 ไม่แสดง)

**ข้อจำกัดที่ยอมรับ (ไม่ใช่สัญญาใหม่):** ป้ายอยู่ในหน่วยความจำของรอบ — รีโหลดหน้ากลางรอบแล้วแถวนั้นถอยไปใช้ method จาก server (อาจเห็น "พิมพ์" แทน "เครื่องยิง/แตะตาราง") · ถ้า PM/FE เห็นว่าติดป้ายเกินขอบ BR-13 → ทางเลือก B (ค่าแนะนำรอง): นับตาม server ล้วน, ผังหน้าสแกน = "พิมพ์", ตัด "แตะตาราง" ออกจากสรุปรอบและแก้ตัวอย่าง BR-14 · **ไม่ต้องให้เจ้าของงานตัดสิน** (ตีความจากเจตนา P1/P2) เว้นแต่เลือกทางเลือก B

## Q-C "ส่งช้า" เมื่อมีรายการรอส่ง (R-3902)

**คำตัดสิน:** เซิร์ฟเวอร์ตัดสิน (BR-13) → เครื่องห้ามเดา และห้ามขึ้น 0 เฉย ๆ (ไม่ทราบ ≠ 0)
- งานไม่มีกำหนดส่ง → ไม่แสดง "ส่งช้า" (เดิม)
- มีกำหนดส่ง · ไม่มีรายการรอส่ง → "ส่งช้า n" (n = ที่ server ตัดสินแล้ว)
- มีกำหนดส่ง · มีรายการรอส่ง p รายการที่เป็น "ส่งแล้ว" ซึ่งยังไม่มีผลตัดสิน → "ส่งช้า n · รอตัดสิน p" (รอตัดสิน = รับแล้วแต่ยังไม่ขึ้นระบบ จึงยังไม่รู้ว่าช้าหรือไม่) · ใส่ `aria-label` เต็ม "ส่งช้า n คน และรอตัดสินอีก p คน"
- รอตัดสินหายเองเมื่อ ack แล้วนับเป็นส่งช้าตามผลจริง
- ตัวอย่าง: กำหนด 1 พ.ย. วันนี้ 12 พ.ย. ออฟไลน์สแกน 20 คน ไม่เคยมีข้อมูล server → "ส่งช้า 0 · รอตัดสิน 20" (ไม่ใช่ "ส่งช้า 0") · ต่อเน็ตส่งครบ → "ส่งช้า 20" · ตัวอย่าง BR-14 เดิม (ไม่มีรอส่ง) → "ส่งช้า 3"
- ไม่เกี่ยวกับการ์ดผลตอนสแกน (ซึ่งบอก "ส่งช้า" จากวันที่รับในเครื่อง เป็นการแจ้งชั่วคราวเดิม ไม่แก้)

## สิ่งที่ FE ต้องแก้ (ไม่แตะ worker/outbox/op/BR-13 logic ของ commitStudent)

1. `state.ts`: เพิ่ม map ป้ายต่อรอบ `roundHow: Map<studentId, method>` (ล้างเมื่อเริ่มรอบ/`resetSubs`) · ตั้งตอนมี op ที่ทำให้นักเรียนเป็นส่งแล้ว **ถ้ายังไม่มีป้ายใน map** (op ใส่คะแนนไม่เขียนทับ) · ลบเมื่อเลิกทำ/ยกเลิกการส่ง/ปฏิเสธ · ผังที่นั่งหน้าสแกนส่งป้าย "grid" เข้า map เท่านั้น (op ยังส่ง "manual") — ผ่านตัวแปรสถานะแยกที่ `makeOp` อ่านตอนเซ็ต `opMethods` · ไม่แก้ `held`/ลำดับตัดสิน
2. `summary.ts`: `roundNumbers` นับ method = `roundHow.get(id) ?? (sub.sid===roundId ? sub.method : undefined)` และเงื่อนไข "ส่งแล้ว" เหมือนเดิม · เพิ่ม `lateWaiting` = จำนวนส่งแล้วที่ยังรอส่ง (มี op ค้าง) ของงานที่มีกำหนดส่ง · `pushRecent` ใช้ map เดียวกันให้ไอคอนตรงกัน
3. `RoundSummary.tsx`: แสดง "ส่งช้า n · รอตัดสิน p" ตาม Q-C (บรรทัด :123, :150) · `next = known && isOpen ? nextRoom(...) : null` (:65-67) · "กลับไปสแกนต่อ" ปิดใช้ + "งานนี้ปิดรับแล้ว" เมื่อ `!isOpen` (:213-217)
4. เทสต์เพิ่ม: ack หลังใส่คะแนน (HID→ใส่คะแนน→ack = เครื่องยิง) · ออฟไลน์ใส่คะแนนแทน op · แตะผัง = แตะตาราง · เลิกทำ · pendingOps บนงานมีกำหนด ≠ "ส่งช้า0" · งานปิด → ไม่มีห้องถัดไป
