# Requirements: วันที่รับงานจริง + แก้ช้า/ทันรายช่อง (c03-submit-date)

โดย System Analyst · 2026-11-02 · สถานะ: ร่าง (รอคำตอบคำถามค้าง 4 ข้อ แล้วจึงเป็น "รออนุมัติ (Gate 1)") · ธง 💰 🔄 🖥

## ปัญหาและเป้าหมาย

ปัญหา: ครูเก็บกระดาษทันกำหนด (เช่น ศุกร์ 30 ต.ค.) แต่มาสแกน/กรอก/กด "ทั้งห้องส่งแล้ว" วันจันทร์ 2 พ.ย. ระบบถือว่าส่งวันจันทร์ → เด็กทั้งห้องกลายเป็น "ส่งช้า" ทั้งที่ไม่ช้า และตอนนี้ครูแก้รายคนไม่ได้ (อ่านโค้ดแล้ว: `submissions.ts` ตั้ง `submitted_at` = เวลาที่ครูบันทึก ทั้งทางสแกน/สมุดคะแนน และทางปุ่มทั้งห้อง; ช่องที่ส่งแล้วถูกกันเปลี่ยนเวลาโดย C-01 และตัว `late` คำนวณใหม่จากเวลานั้นเทียบกำหนดส่งเสมอ)

เป้าหมาย: (1) ครูเลือก "วันที่รับงานจริง" ตอนสแกน/ตอนกดทั้งห้อง (2) แก้วันที่รับงานของช่องที่ส่งแล้วรายคนในสมุดคะแนน โดยคะแนนไม่เปลี่ยน (3) "ช้า/ทัน" ยังคำนวณจากวันที่เทียบกำหนดส่งตามกฎเดิม ไม่มีใครตั้ง "ช้า" ตรงๆ (4) ไม่ต้อง migration

ผลอ่านโค้ดที่มีผลต่อการออกแบบ: ① `submitted_at` มีอยู่แล้วใน `0001_init.sql` และอยู่ใน `Submission`, `GET submissions`, audit, backup/restore ครบ → ไม่ต้องเพิ่มคอลัมน์ ② `clampClientTs` (ไม่เกินตอนนี้ ไม่เก่ากว่า 7 วัน) ใช้ทั้งเป็น "เวลาที่ครูทำ" (`event_at` ตัดสินใครชนะ) และเป็น `submitted_at` → ต้องแยก 2 อย่างนี้ ③ `opSchema` เป็น zod object ธรรมดา: ฟิลด์ที่ไม่รู้จักถูกตัดทิ้งเงียบๆ ไม่ error ④ ข้อมูลผิดใน schema ทำให้ทั้ง request (≤ 50 op) ล้ม → ค่าวันที่ต้องตรวจเป็นรายผล op ไม่ใช่ใน schema ⑤ สมุดคะแนนพิมพ์คะแนนช่องว่าง = รับงานด้วยเวลา "ตอนนี้" เช่นกัน (method `grid`) ⑥ `Gradebook.tsx` เก็บ `Sub` แค่ status/score/late ไม่มี `submitted_at`

## User stories

- US-01: ในฐานะครู ฉันต้องการเลือกวันที่รับงานตอนสแกน เพื่อให้เด็กที่ส่งทันกำหนดไม่ถูกนับช้าเพราะฉันสแกนทีหลัง
- US-02: ในฐานะครู ฉันต้องการกด "ทั้งห้องส่งแล้ว" พร้อมวันที่รับงาน และย้อนกลับได้ เพื่อไม่ต้องแก้ทีละคน
- US-03: ในฐานะครู ฉันต้องการแก้วันที่รับงานของช่องที่ส่งแล้วในสมุดคะแนน (คะแนนไม่เปลี่ยน ย้อนกลับได้) เพื่อสลับสถานะ ช้า/ทัน รายคน
- US-04: ในฐานะครู ฉันต้องการเห็นวันที่รับงานและคำว่า ส่งทัน/ส่งช้า ที่มาจากวันนั้น และตัวเลขช้าในรายงาน/Excel ตรงกัน
- US-05: ในฐานะครู ฉันต้องการให้คิวออฟไลน์และแอปรุ่นเก่ายังทำงานถูก ไม่ทำให้คะแนนหรือวันที่เพี้ยน

## กฎธุรกิจ

### BR-01 กฎเดิมที่ต้องคงไว้ (M1-04 BR-04 + C-01)
`late` = 1 เมื่อและเฉพาะเมื่อ status submitted, มี `submitted_at`, งานมีกำหนดส่ง, และ **วันที่ไทย (UTC+7) ของ `submitted_at` > กำหนดส่ง** · ไม่มี API ใดรับค่า `late` จากผู้ใช้ · `late` ถูกตัดสินใหม่ทุกครั้งที่เขียนช่อง (`lateFixForCells`) และเมื่อเลื่อนกำหนดส่ง (`lateFixForAssignment`) · งานนี้ **ไม่แตะ** นิยามนี้ · ตัวอย่าง: กำหนด 10-30, submitted_at 10-30 12:00 ไทย → 0 · 10-31 12:00 → 1 · ไม่มีกำหนดส่ง → 0 เสมอ

### BR-02 "วันที่รับงาน" และการเก็บ
- เป็นฟิลด์ใหม่ไม่บังคับใน op และ bulk ชื่อที่แนะนำ `receivedDate` รูป `YYYY-MM-DD` ค.ศ. วันที่ปฏิทินไทย
- **เก็บใน `submitted_at` เดิม ไม่มีคอลัมน์ใหม่** วิธีคำนวณเมื่อช่องกลายเป็น submitted ครั้งแรก (e = `clampClientTs(clientTs, now)` ใช้เป็น `event_at` เหมือนเดิม): ถ้า `receivedDate` ไม่มี → `submitted_at` = e (เหมือนเดิม) · ถ้า `receivedDate` = วันที่ไทยของ e → `submitted_at` = e (เวลาจริง) · นอกนั้น → `submitted_at` = min(12:00 ไทยของวันนั้น, now) · เที่ยงทำให้วันที่ไทยเท่าที่เลือกเสมอ ไม่ข้ามวันเพราะเขตเวลา
- ตรวจ (เมื่อมี `receivedDate`) เรียง: รูปแบบ ค.ศ. 1900–2099 เป็นวันจริงตามปฏิทิน (ตัวตรวจเดียวกับ `restore-validation`) → `received_date_invalid` · ไม่เกินวันนี้ตามเวลาไทยของ server (ณ ตอนเขียน) → `received_date_future` · **ไม่ก่อนวันมอบหมาย** ของงาน ถ้างานมี `assigned_date` → `received_date_before_assigned` (คำถามค้างข้อ 2) · ผิด = ผลของ op นั้นเป็น `invalid`+reason ไม่ใช่ error ทั้งคำขอ (bulk: 400 รหัสเดียวกัน)
- ตัวอย่างวัน 11-02 09:00: `"2026-10-30"` → 2026-10-30T05:00Z · `"2026-11-02"` clientTs 09:00 → 09:00 · `"2026-11-03"` → future · `"2026-10-25"` (มอบหมาย 10-26) → before_assigned · `"2026-02-30"` → invalid · เลือกวันนี้ผ่านแอปขณะ 00:30 ไทยที่ server ยังเป็นวันก่อน (นาฬิกาเพี้ยน) → future (แอปใช้เวลาแก้เทียบ server อยู่แล้ว)

### BR-03 ช้า/ทัน ยังเป็นผลคำนวณ — "สลับช้า" = แก้วันที่
ครูสลับช้า/ทันของช่องหนึ่งโดย **เปลี่ยนวันที่รับงาน** เท่านั้น แล้ว `late` ถูกคำนวณจากวันนั้นตาม BR-01 · ไม่มีค่า "ช้า/ไม่ช้า" ที่ครูตั้งเองแยกจากวันที่ · ทางลัด "ตามกำหนดส่ง" = ตั้งวันที่รับงานเป็นวันกำหนดส่ง (ถ้ามี) · ไม่มีทางลัด "ตั้งให้ช้า" · วันที่ที่เก็บคือ "วันที่นับว่ารับงาน" ซึ่งครูอาจตั้งให้เท่ากำหนดส่งเพื่อให้อภัยการช้า — ระบบไม่แยก "วันจริง" กับ "วันที่นับ" (ดูคำถามค้างข้อ 1) · ตัวอย่าง: ก รับ 11-02 (late) → แก้เป็น 10-30 → ทัน · เลื่อนกำหนดส่งภายหลัง วันที่รับงานไม่เปลี่ยน `late` คำนวณใหม่

### BR-04 การรับงานซ้ำไม่แก้วันที่ (ผูก C-01)
op รับงาน (method camera/hid/manual) ที่มาถึงช่อง submitted → `already_submitted` ตาม C-01 เสมอ ไม่ว่ามี `receivedDate` · op คะแนนที่พิมพ์หลังรับงานในรอบเดียวกัน (ข้อยกเว้น C-01 BR-02) ไม่เปลี่ยน `submitted_at` · วันที่ใน op ใช้ได้เฉพาะตอนช่องกลายเป็น submitted ครั้งแรก (ไม่มีแถว/void/excused) หรือเป็น op แก้วันที่ตาม BR-05 · ตัวอย่าง: ก submitted 10-29, hid + `"2026-10-30"` → ช่องไม่เปลี่ยน

### BR-05 การแก้วันที่ช่องที่ส่งแล้ว (เจตนา "grade")
- op method `grid` + `dateOnly: true` + `receivedDate` (นับเป็นงานของครู ไม่ใช่การรับงาน: ไม่ถูก `already_submitted` กั้น, ทำได้แม้งานปิดรับ, เด็กที่ย้ายออกก็ทำได้ตามกฎ D15/D23)
- ทำได้เฉพาะช่องที่ status = submitted ณ ตอนเขียน มิฉะนั้น `invalid` `cell_not_submitted` (ห้ามสร้างการรับงานโดยบังเอิญ เช่นช่องถูกล้างจากเครื่องอื่นระหว่างทาง) · method ที่เป็นรับงาน + `dateOnly` → `invalid` `redate_not_allowed` (กันคำขอปลอมข้ามกฎ C-01)
- ผล: `submitted_at` ใหม่ตาม BR-02 · score/status จากแถวในระบบ **ไม่ใช้ score ใน op** · `late` คำนวณตาม BR-01 · วันที่ใหม่ = วันที่ไทยเดิมของ `submitted_at` → คง `submitted_at` เดิม (ไม่ถูกเปลี่ยนเป็นเที่ยง) · เวลาสู้กันใช้ `event_at` ตามระบบเดิม
- audit 1 แถว (update) ก่อน/หลังครบ 10 ฟิลด์ · ตัวอย่าง: ก 7, 11-02 09:00, late 1 → แก้ 10-30 → 7, 10-30 12:00, late 0

### BR-06 ทั้งห้องส่งแล้วพร้อมวันที่ และย้อนกลับ
`bulk` action all-submitted รับ `receivedDate` ไม่บังคับ ใช้ตาม BR-02 กับทุกช่องที่ถูกเปลี่ยน (ช่อง submitted/excused ถูกข้ามเหมือนเดิม) · ฟิลด์นี้กับ action อื่น → 400 · audit รายช่องเก็บ before/after รวม `submitted_at` · `bulk-undo` คืนค่า `submitted_at` เดิมตามที่เก็บ (ตรงทุก ms) และ `late` ถูกตัดสินใหม่จากกำหนดส่งปัจจุบัน (กลไกเดิม) · ย้อนไม่ได้ถ้าช่องถูกแก้หลังนั้น (`modified_since` เช็ก `submitted_at`) รวมถึงแก้วันที่ · ตัวอย่าง AC-09/11

### BR-07 ออฟไลน์และทำซ้ำ
op เก็บ `receivedDate` เป็นสตริงวัน (ไม่ใช่เวลา) → ส่งซ้ำกี่วันผลเดิม · แอปใส่ `receivedDate` ให้ **ทุก op รับงาน** ใหม่ (ค่าที่ครูเลือก หรือ "วันนี้" ตามเวลาแก้เทียบ server ณ ตอนทำ) เพื่อไม่ให้การ clamp 7 วันเปลี่ยนวันที่ · ตรวจ BR-02 ตอนเขียน (ไม่ใช่ตอนทำ) → op ค้างนานที่กลายเป็นผิด (เช่นครูแก้วันมอบหมายหลังจากนั้น) เข้า "ส่งไม่สำเร็จ" พร้อมเหตุผลภาษาไทย ครูกดลองใหม่/ทิ้งได้ · `opId` เดิมซ้ำ = `duplicate` · ตัวอย่าง AC-06, AC-18

### BR-08 ความเข้ากันได้
ทุกฟิลด์ใหม่ไม่บังคับ · ไม่ส่ง = ทำงานเหมือนเดิมเป๊ะ · ผลชนิดใหม่ไม่มี (ใช้ `invalid`+reason ซึ่งแอปเก่าเข้าใจเป็น "ส่งไม่สำเร็จ") · **ลำดับปล่อย: server ก่อน แล้วค่อยแอป** (server เก่า + แอปใหม่ จะตัดฟิลด์ทิ้งเงียบๆ แล้วลงเวลาตอนนี้ — ห้ามเกิด) · EP-02 ไม่เปลี่ยน (คืน `submitted_at` อยู่แล้ว)

### BR-09 ย้อนกลับการแก้วันที่ (สมุดคะแนน)
ย้อนกลับ = op แก้วันที่อีกตัวด้วยวันที่เดิม (วันที่ไทยของ `submitted_at` เดิม) คืนวันที่และ `late` เดิม · เวลาในวันของช่องที่เดิมเป็นเวลาจริงอาจกลายเป็น 12:00 (ยอมรับ ไม่มีผลต่อ `late`) · ถ้ามีการแก้ช่องอื่นแทรก ย้อนไม่ได้ตาม `superseded` · ตัวอย่าง AC-16

### BR-10 ผลต่อตัวเลข 💰
เปลี่ยนเฉพาะ `late` (นับช้า, เครื่องหมายช้าในสมุดคะแนน/ผังเลขที่/Excel C-08) · **ไม่เปลี่ยน** คะแนน คะแนนสะสม จำนวนส่ง และ "ค้าง" เพราะ metrics (`shared/metrics.ts`) นับช้าเป็นส่งแล้วมีคะแนน · ตัวอย่าง AC-20: ช้า 30 → 2 ส่วน 240/300 = 80% คงเดิม

### BR-11 ไม่ต้อง migration
ยืนยัน: `submitted_at` (INTEGER ms) มีใน `0001_init.sql`, `mapSubmission`, audit, backup/restore (`restore-validation`: `optionalStamp`) · ใช้ได้ครบทุกกรณีใน AC · **จะต้องมีคอลัมน์เมื่อเลือกคำถามค้างข้อ 1 ทาง ข** เท่านั้น (เก็บ "วันที่จริง" แยกจาก "ยกเว้นช้า") — ห้ามถือเป็นสมมติฐาน ต้องให้เจ้าของงานตัดสินและขออนุมัติ migration แยก

## ไม่ทำในรอบนี้

- คอลัมน์ `late_override` / เก็บ "วันที่จริง" แยกจาก "วันที่นับ" (ขึ้นกับคำถามข้อ 1) · ตั้ง "ช้า/ไม่ช้า" ตรงๆ โดยไม่แก้วันที่ · ทางลัด "ตั้งให้ช้า"
- เวลาในวัน (ชั่วโมง) ของการรับงาน · เลือกวันที่รายคนก่อนสแกนในหน้าสแกน (เลือกวันที่ระดับรอบเท่านั้น; รายคนใช้แก้วันที่ในสมุด)
- แก้วันที่หลายช่องพร้อมกัน (เลือกหลายช่อง) นอกจากปุ่มทั้งห้องส่งแล้ว · วันที่รับงานเมื่อพิมพ์คะแนนช่องว่างในสมุดคะแนน (ได้ "ตอนนี้" เหมือนเดิม แล้วแก้วันที่ได้ — คำถามข้อ 3) · ปิดรอบ/สรุปรอบสแกน · C-02/C-05 · ค่าปรับหรือการหักคะแนนเพราะช้า (ไม่มีอยู่ในระบบ)

## สมมติฐาน

- เวลา "วันนี้" ของฝั่ง server = เวลาไทย UTC+7 ไม่มี DST (`bkkToday`) · แอปใช้ `actionTime()` ที่แก้เวลาเทียบ server แล้ว
- เจ้าของงานใช้ "วันที่รับงาน" เป็นวันที่ปฏิทินเท่านั้น ไม่ต้องการเวลา (คำตอบ Gate 0: "เลือกวันที่")
- เทสต์เดิมที่สมมติว่า bulk/สแกนทุกครั้งประทับ "ตอนนี้" ยังผ่าน (ไม่ส่งฟิลด์ = เดิม)
- ไม่ได้รันโค้ดหรือ trace-check ในรอบนี้ (อ่านโค้ดอย่างเดียว) → สถานะ NOT RUN
