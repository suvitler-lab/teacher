# Requirements: เพิ่มคะแนนเต็มแล้วถามปรับคนที่ได้เต็มเดิม (integrity-c02)

โดย System Analyst · 2026-11-02 · สถานะ: อนุมัติ (Gate 1 2 พ.ย. — Q1 ข, Q2 ก, Q3 ก ตามค่าแนะนำ)

## ปัญหาและเป้าหมาย

ปัญหา: ครูสแกนรับงานโหมด "ให้เต็ม" ที่เต็ม 10 แล้วภายหลังแก้งานเป็นเต็ม 20 → คนที่ได้ 10 (เต็มเดิม) ค้างเป็น 10/20 ทั้งห้องโดยไม่มีอะไรเตือน ร้อยละของงานและคะแนนสะสมของเด็กลดลงเงียบๆ (ระบบกันเฉพาะการลดคะแนนเต็ม)

เป้าหมาย: ทุกครั้งที่เพิ่มคะแนนเต็มและมีคนได้เต็มเดิม ครูถูกถามด้วยกล่องยืนยันแบบเดิมของแอปว่าจะปรับคนเหล่านั้นเป็นเต็มใหม่ไหม (ค่าเริ่มต้น = ปรับ ตาม D32) ผลลงพร้อมกันครั้งเดียว มีประวัติทุกช่อง และพฤติกรรมอื่นไม่เปลี่ยน

ผลอ่านโค้ด (branch c01 ที่ checkout หลัก — worktree นี้ยังเป็นโค้ดเก่า): `POST /api/assignments` อ่านงานเดิม → ถ้า **ลด** และมี score > เต็มใหม่ ตอบ `409 score_over_full` (เช็กซ้ำใน batch ด้วย `abortIf(lowersBelowScores)`) → upsert งาน + ห้อง + `lateFixForAssignment` + audit งาน 1 แถว ใน `batchAtEpoch` เดียว · ไม่มีอะไรแตะ `submissions.score` เมื่อเพิ่ม · แก้งานเปิดจากสมุดคะแนนที่เดียว (`Gradebook.tsx` ~705 → `AssignmentModal`, onSaved โหลดใหม่อยู่แล้ว)

## User stories

- US-01: ในฐานะครู เมื่อฉันเพิ่มคะแนนเต็มของงาน ฉันต้องการถูกถามว่าจะปรับคนที่ได้เต็มเดิมเป็นเต็มใหม่ไหม เพื่อคะแนนสะสมไม่ผิดเงียบๆ
- US-02: ในฐานะครู ฉันต้องการให้การปรับลงครบทุกคนพร้อมคะแนนเต็มใหม่หรือไม่ลงเลย และตรวจย้อนได้ว่าช่องไหนถูกปรับ เพื่อเชื่อถือตัวเลขได้
- US-03: ในฐานะครู ฉันต้องการให้การแก้งานแบบอื่น (ลดคะแนนเต็ม แก้ชื่อ แก้วัน) และการสแกนทำงานเหมือนเดิม

## กฎธุรกิจ

### BR-01 "คนที่ได้เต็มเดิม"

แถวใน submissions ของงานนั้น (ทุกห้องที่มอบงาน ทุกสถานะนักเรียน รวม moved/finished · ทุก method) ที่ **status = submitted และ score = คะแนนเต็มเดิม** โดย "คะแนนเต็มเดิม" = full_score ในฐานข้อมูล ณ ตอนเขียน · ไม่นับ: excused, void, ไม่มีคะแนน (รอตรวจ), คะแนนน้อยกว่าเต็มเดิม, ไม่มีแถว, op ที่ยังค้างในคิวของเครื่อง · ส่งช้า (late) นับ · งานปิดรับแล้วก็ถาม (ปิดรับกันเฉพาะรับงาน)

ตัวอย่าง (F, เต็ม 10): ก 10 ✓ · ข 10 late ✓ · ซ 10 ห้อง 2 moved ✓ · ค 7 ✗ · ง ว่าง ✗ · จ excused ✗ · ฉ void ✗ · ช ไม่มีแถว ✗ → 3 คน

### BR-02 เมื่อไรถาม และผลของแต่ละทางเลือก

ถามเมื่อ: แก้งานที่มีอยู่ **และ** เต็มใหม่ > เต็มเดิม **และ** คนที่ได้เต็มเดิม ≥ 1 · "ปรับ" → score ของคนเหล่านั้น = เต็มใหม่ · status, late, submitted_at ไม่เปลี่ยน · updated_at/event_at = เวลาบันทึก · method = bulk (เหมือนปุ่ม "ให้เต็มทั้งห้อง" — Tech Lead ยืนยัน) · "คงไว้" → ไม่แตะช่องใด

ตัวอย่าง: ก {submitted, 10, late 0, 09:00} เต็ม 10 → 20 · ปรับ → ก {submitted, 20, late 0, 09:00} · คงไว้ → ก {submitted, 10, late 0, 09:00} แสดง 10/20

### BR-03 ผลต่อร้อยละ (เหตุที่ต้องถาม)

สูตรเดิม (shared/metrics.ts): ร้อยละงาน = Σคะแนน ÷ (จำนวนที่มีคะแนน × เต็ม) · สะสมรายคน = Σคะแนน ÷ Σเต็มของงานที่มีคะแนน + งานค้าง (นับ 0) · ปัดด้วย Math.round

- ร้อยละงาน a1 ห้อง 1 (ก 10, ข 10, ค 7 มีคะแนน 3 คน): ก่อน 27/30 = 90% · ปรับ 47/60 = 78% (78.33) · คงไว้ 27/60 = 45%
- สะสมของ ก (a1 + งาน b 8/10): ก่อน 18/20 = 90% · ปรับ 28/30 = 93% (93.33) · คงไว้ 18/30 = 60%
- เด็กค้างส่ง a1 ที่เลยกำหนด: 0/10 → 0/20 ทั้งสองทางเลือก (ตัวหารเพิ่มตามเต็มใหม่ เป็นพฤติกรรมเดิม)

### BR-04 ลงพร้อมกันครั้งเดียว + ประวัติต่อช่อง

คะแนนเต็มใหม่, ช่องที่ปรับ, audit ช่องละ 1 แถว (before/after ของช่อง) และ audit ของงาน (เต็มเดิม→ใหม่, ทางเลือก, จำนวน) อยู่ใน transaction/batch เดียวกับการแก้งาน (`batchAtEpoch`) ใช้ batch_id เดียวกัน · guard เดิมทุกตัว (epoch, ลดต่ำกว่าคะแนน, ห้องผิดปี, วันที่) ล้ม = ไม่มีอะไรลงเลย

ตัวอย่าง: ปรับ 3 คนสำเร็จ → audit ใหม่ 4 แถว (งาน 1 + ช่อง 3) batch_id เดียวกัน · epoch เปลี่ยน → audit ใหม่ 0 แถว full ยัง 10

### BR-05 ตัดสินจากข้อมูลตอนเขียน

ชุดคนที่ปรับเลือกในคำสั่งเขียน (score = เต็มเดิมในฐานข้อมูล ณ ตอนนั้น) ไม่ใช้รายชื่อจากเครื่อง · จำนวนในกล่องถามมาจาก server ตอนกดบันทึก · ถ้าคะแนนเต็มในฐานข้อมูลไม่เท่ากับเต็มเดิมที่ครูเห็นตอนถาม → ไม่ลงอะไรเลย ตอบ 409 ให้โหลดใหม่

ตัวอย่าง: ถาม 3 คน ระหว่างนั้นมีคนได้ 10 เพิ่ม 1 → ปรับ 4 ผลบอก 4 · อีกเครื่องเปลี่ยนเต็มเป็น 15 → 409 ไม่ลง

### BR-06 op ค้างคิวที่ใช้คะแนนเต็มเก่า

`/api/submissions/batch` ไม่เปลี่ยน: op ที่ `fullScoreAtScan` ≠ เต็มปัจจุบัน → `full_score_changed` ไม่บันทึก ไปรายการ "ส่งไม่สำเร็จ" · การปรับไม่ครอบคลุม op ที่ยังไม่ถึง server · หมายเหตุ: "ลองใหม่" ส่งเต็มเดิมซ้ำจึงล้มซ้ำ ครูต้องกรอกในสมุดคะแนน (พฤติกรรมเดิม)

ตัวอย่าง: คิวมี ฌ 10 (เต็ม 10) · server เต็ม 20 แล้ว → `full_score_changed`, currentFullScore 20, ฌ ไม่มีแถว

### BR-07 กรณีอื่นคงพฤติกรรมเดิม

ลดคะแนนเต็ม → มี score > เต็มใหม่ = `409 score_over_full` (over = จำนวน) ไม่มีกล่องถาม · ลดได้ = บันทึกทันที · เท่าเดิม/สร้างงานใหม่/คัดลอกงาน = ไม่ถาม · เพิ่มแต่ไม่มีคนได้เต็มเดิม = ไม่ถาม

ตัวอย่าง: a3 เต็ม 20 (ก 20, ค 15) → ลดเป็น 10 → 409 over 2 · a4 (ค 8) → ลดเป็น 10 → บันทึก ค ยัง 8

### BR-08 กล่องถาม

ใช้ Dialog เดิมแบบกล่องยืนยันปุ่มทั้งห้อง (ไม่ออกแบบใหม่) · เนื้อหาต้องมี: ชื่องาน, จำนวนคน, เต็มเดิม → เต็มใหม่, ผลของ "คงไว้" (เช่น 10/20) · ปุ่ม: ยกเลิก / คงไว้ / ปรับ (ปุ่มหลัก = ค่าเริ่มต้นที่แนะนำ ตาม D32) · ยกเลิก = ไม่ส่งคำขอ กลับฟอร์ม · ข้อความเสนอ (Designer ปรับถ้อยคำได้): หัว "ปรับคนที่ได้เต็ม 3 คน?" · เนื้อ "ใบงานที่ 5 · 3 คนได้ 10/10 (เต็มเดิม) ปรับเป็น 20/20 หรือคงไว้เป็น 10/20" · ปุ่ม "ปรับเป็น 20/20" · "คงไว้ 10/20" · "ยกเลิก" · หลังบันทึก: "บันทึกแล้ว · ปรับเป็นเต็มใหม่ 3 คน"

ตัวอย่าง: 1 คน → "ปรับคนที่ได้เต็ม 1 คน?" · 45 คน → "ปรับคนที่ได้เต็ม 45 คน?"

### BR-09 ย้อนกลับการปรับ (ตามคำถามค้างข้อ 1 ค่าแนะนำ)

หลังปรับสำเร็จ ข้อความมีปุ่ม "ย้อนกลับ" (แบบเดียวกับหลัง "ล้างทั้งห้อง") → คืนเฉพาะคะแนนของช่องที่ปรับเป็นค่าเดิม คงคะแนนเต็มใหม่ · ช่องใดถูกแก้หลังปรับ → `409 modified_since` ไม่ย้อนเลย · ย้อนซ้ำ = ไม่เปลี่ยนอะไร · ถ้าต้องการเต็มเดิมด้วย ครูแก้งานเป็น 10 ต่อ (ผ่านเพราะไม่มีใครเกิน 10)

ตัวอย่าง: ปรับ ก, ข, ซ 10 → 20 แล้วย้อน → 10, 10, 10 (เต็ม 20 แสดง 10/20) → แก้งานเป็นเต็ม 10 → บันทึกได้ (ไม่มีกล่องถามเพราะเป็นการลด)

### BR-10 แอปรุ่นเก่า (ตามคำถามค้างข้อ 3 ค่าแนะนำ)

คำขอแก้งานที่ไม่ระบุทางเลือก + เพิ่มเต็ม + มีคนได้เต็มเดิม ≥ 1 → server ไม่บันทึก ตอบ 409 ข้อความไทยให้อัปเดตแอป · ไม่ระบุทางเลือกแต่ไม่ต้องถาม (ไม่มีคนได้เต็มเดิม, ลด, เท่าเดิม, สร้างใหม่) → บันทึกเหมือนเดิม · request เดิมยังผ่าน schema

ตัวอย่าง: แอปเก่าเพิ่ม a1 เป็น 20 (มี 3 คน) → 409 "มี 3 คนได้คะแนนเต็มเดิม — อัปเดตแอปแล้วบันทึกอีกครั้ง" · a2 (ไม่มีใครได้ 10) → 200
