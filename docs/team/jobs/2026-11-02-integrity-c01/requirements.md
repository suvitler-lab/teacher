# Requirements: คะแนนไม่ถูกเขียนทับเมื่อสแกนช่องที่ส่งแล้ว (integrity-c01)

โดย System Analyst · 2026-11-02 · สถานะ: ร่าง (รอคำตอบคำถามค้าง 3 ข้อ แล้วจึงเป็น "รออนุมัติ (Gate 1)")

## ปัญหาและเป้าหมาย

ปัญหา: ถ้าเด็กสแกนบัตรซ้ำ (หรือครูแตะผังเลขที่) บนเครื่องที่ยังไม่รู้ว่าเด็กคนนั้นส่งแล้ว ระบบจะบันทึกทับคะแนนที่มีอยู่เงียบๆ โหมดเต็มทับเป็นคะแนนเต็ม โหมดให้คะแนนทีหลังลบคะแนนเป็น "รอตรวจ" — ครูไม่รู้ตัวและคะแนนสะสมผิด

เป้าหมาย: ช่องที่ "ส่งแล้ว" จะไม่ถูกการสแกนเปลี่ยนเลย ไม่ว่าจะมาจากเครื่องไหน ออนไลน์หรือคิวออฟไลน์ ครูเห็น "ส่งไปแล้ว — ไม่บันทึกซ้ำ" เหมือนสแกนซ้ำบนเครื่องเดียวกัน และยังแก้คะแนนโดยตั้งใจจากสมุดคะแนนได้ตามเดิม

### ผลการอ่านโค้ด: ยืนยันว่า C-01 เกิดได้จริง (อ่านโค้ด ยังไม่ได้รัน — Dev ต้องเขียนเทสต์ให้ล้มก่อนแก้)

ทางเดินของการสแกน: `Scan.tsx` handleScan/แตะผังเลขที่ → `commitStudent` → กันซ้ำเฉพาะเมื่อ `effSub` (ข้อมูลในเครื่อง = ผลดึงล่าสุดทุก 60 วิ + คิวของเครื่องนี้) บอกว่า "ส่งแล้ว" → `makeOp` (method camera/hid/manual, score = เต็มหรือ null) → `outbox.ts` → `POST /api/submissions/batch` → `judge` ไม่ดูสถานะช่อง → ผ่านการเทียบเวลา (event_at) เพราะการสแกนเกิดทีหลัง → `wasSubmitted` เก็บเวลาส่ง/ช้าเดิม แต่ **score, method, device_id, scan_session_id, updated_at, event_at ถูกทับ** และเขียน audit เป็น "update"

เงื่อนไขที่ทำให้เกิด: เครื่องที่สแกน "ไม่รู้" ว่าเด็กส่งแล้ว — คือการส่ง/ให้คะแนนเกิดจากที่อื่น (สมุดคะแนน, ปุ่มทั้งห้อง, รอบสแกนบนอีกเครื่อง) และเครื่องนี้ยังไม่ดึงข้อมูลใหม่ (≤ 60 วิ, ออฟไลน์, โหลดไม่สำเร็จ) ถ้าเครื่องนี้สแกนเด็กเองในรอบเดียวกัน จอกันไว้แล้ว

## User stories

- US-01: ในฐานะครู ฉันต้องการให้การสแกนเด็กที่ส่งแล้วไม่เปลี่ยนคะแนนหรือเวลาส่ง ไม่ว่าเครื่องที่สแกนจะมีข้อมูลเก่าหรือออฟไลน์ เพื่อให้คะแนนสะสมถูกต้อง
- US-02: ในฐานะครู ฉันต้องการแก้คะแนนในสมุดคะแนน และใส่คะแนนหลังรับงานในโหมดทีละคนได้ตามเดิม เพื่อไม่ให้การป้องกันขวางงานปกติ

## กฎธุรกิจ

### BR-01 ช่องที่ "ส่งแล้ว" ไม่รับงานซ้ำ

op "รับงาน" (status submitted และ method camera/hid/manual — server ตัดสินจาก method ไม่เชื่อ intent) ที่มาถึงช่องซึ่ง status = submitted อยู่แล้ว → ไม่บันทึก ตอบ `already_submitted` พร้อมค่าปัจจุบันของช่อง · ช่องเดิมทั้ง 9 ฟิลด์และ audit ไม่เปลี่ยน · ต้องจริงแม้มีคำขอสองเครื่องแข่งกัน (ตัดสินกับค่าที่อยู่ในฐานข้อมูลตอนเขียน) · ยกเว้นตาม BR-02

ตัวอย่าง: ช่อง ก = {submitted, 7, late 0, submitted_at 09:00, grid} + op hid score 10 เวลา 09:00:20 → ผล `already_submitted`, submission.score = 7, ช่องยัง {submitted, 7, late 0, 09:00, grid}

### BR-02 ใส่คะแนนครั้งแรกหลังรับงานในรอบเดียวกัน (ข้อยกเว้นของ BR-01)

op รับงานที่มีคะแนน บันทึกได้แม้ช่องเป็น submitted เมื่อครบทุกข้อ: (1) ช่องถูกเขียนล่าสุดโดยการรับงานของรอบสแกนเดียวกัน (scanSessionId ตรงกัน method camera/hid/manual) (2) ช่องยังไม่มีคะแนน (3) op มีคะแนน — คือโหมดทีละคนที่พิมพ์คะแนนหลังสแกน · ถ้าระหว่างนั้นช่องถูกเปลี่ยนจากที่อื่น ข้อ (1) ไม่จริง → ใช้ BR-01

ตัวอย่าง: R1 รับ ค (null, hid) → R1 พิมพ์ 8 (manual) → ค = 8 `ok` · R2 รับ ก ที่เป็น 7 จากสมุด → `already_submitted`, R2 พิมพ์ 6 → ช่องยังเป็น 7 (grid ไม่ใช่รอบ R2) → `already_submitted` · R1 สแกน ค ซ้ำหลังมีคะแนน 8 → ข้อ (2) ไม่จริง → `already_submitted`

### BR-03 การแก้คะแนนโดยตั้งใจไม่ถูกบล็อก

op method grid (สมุดคะแนน), status void หรือ excused, ปุ่มทั้งห้อง และย้อนกลับ ทำงานเหมือนเดิมทุกอย่าง · การแก้คะแนนในช่องที่ส่งแล้วยังคงเวลาส่งและสถานะช้าเดิม

ตัวอย่าง: ก = {submitted 10, submitted_at 09:00, late 0} + grid score 7 เวลา 10:00 → `ok`, ก = {submitted 7, submitted_at 09:00, late 0}

### BR-04 ผลต่อคะแนนสะสม (เหตุที่ต้องกัน)

คะแนนสะสม = Σคะแนน ÷ Σคะแนนเต็มของงานที่มีคะแนน (งาน "รอตรวจ" ไม่นับ) · ก: งาน 1 = 7/10, งาน 2 = 8/10 → 15/20 = 75%

- บั๊กโหมดเต็ม: งาน 1 กลายเป็น 10 → 18/20 = 90% (สูงเกินจริง 15 จุด)
- บั๊กโหมดทีหลัง: งาน 1 กลายเป็นรอตรวจ → 8/10 = 80% และ "ส่งแล้วมีคะแนน" ลด 1
- หลังแก้: ทั้งสองกรณียัง 15/20 = 75%

### BR-05 ช่องที่ยังไม่ "ส่งแล้ว" คงพฤติกรรมเดิม

ไม่มีแถว / void → รับงานได้ เวลาส่ง = เวลาสแกน · excused → ยังกลายเป็น submitted เหมือนเดิม (การเตือนแล้วให้ยืนยันเป็นงาน C-06 ตาม D33 — งานนี้ต้องไม่เปลี่ยนพฤติกรรมนี้)

ตัวอย่าง: ก = {void} + hid 10 เวลา 11:00 → `ok`, ก = {submitted 10, submitted_at 11:00}

### BR-06 ลำดับการตัดสินผลต่อ op

`duplicate` (opId เคยบันทึก) → `epoch_changed` → ผลปฏิเสธเดิม (assignment_missing/invalid, `full_score_changed`, `assignment_closed`, `not_in_class`, `student_inactive`, score_out_of_range) → `superseded` → `already_submitted` → `ok` · แต่ละ op ในคำขอเดียวตัดสินแยกกัน ตามสภาพที่ op ก่อนหน้าในคำขอทิ้งไว้

ตัวอย่าง: ก = submitted 7, งานปิดรับ + op hid → `assignment_closed` (ไม่ใช่ `already_submitted`)

### BR-07 `already_submitted` เป็นคำตอบสุดท้าย ไม่ใช่ความล้มเหลว

ฝั่งเครื่อง: เอาออกจากคิวเหมือน `ok`/`duplicate` ไม่เข้ารายการ "ส่งไม่สำเร็จ" ไม่กั้น op ต่อไปของช่องเดียวกัน · หน้าสแกนแสดงค่าจากระบบและข้อความเดียวกับสแกนซ้ำในเครื่อง ("ส่งไปแล้ว — ไม่บันทึกซ้ำ") · ส่ง opId เดิมซ้ำได้คำตอบเดิมตราบที่ช่องยังเป็น submitted

ตัวอย่าง: คิวรอส่ง 3 รายการ หนึ่งในนั้นได้ `already_submitted` → รอส่ง 2 → 0 หลังส่งครบ · "ส่งไม่สำเร็จ" ยัง 0

### BR-08 ความเข้ากันได้ของสัญญา

`POST /api/submissions/batch`: request เหมือนเดิม (ไม่เพิ่มฟิลด์บังคับ) · response เพิ่มผลชนิดใหม่ `{ opId, result: "already_submitted", submission }` เท่านั้น ผลอื่นและ HTTP status เดิมไม่เปลี่ยน · endpoint อื่นไม่เปลี่ยน · แอปรุ่นเก่าที่ไม่รู้จักผลใหม่: outbox เดิมจัดเป็น "ส่งไม่สำเร็จ" ด้วยเหตุผล `already_submitted` (ข้อมูลไม่ผิด ครูกดทิ้งได้) จนกว่าจะกดอัปเดตแอป

ตัวอย่าง: แอปเก่าส่ง op รับงาน ก ที่เป็น 7 → server ก ยัง 7 · แอปเก่าแสดง 1 รายการใน "ส่งไม่สำเร็จ"

## ข้อจำกัดกลาง

ไม่มี migration (ใช้คอลัมน์เดิม status/score/method/scan_session_id) · ฟรีเทียร์ · คงหน้าตาหน้าสแกนเดิม (D29) ใช้การ์ด/ข้อความ/เสียงสแกนซ้ำที่มีอยู่ · การกันต้องอยู่ที่ server ด้วย ไม่พึ่งข้อมูลในเครื่อง · เขียนเทสต์ที่ล้มก่อนแก้ (ฉ1–ฉ6) · ใช้ fixture ไม่ใช้ข้อมูลเด็กจริง · ห้าม deploy/push/merge จนเจ้าของงานสั่ง
